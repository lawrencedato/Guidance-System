B. Concurrency Control & Deadlock Prevention Plan

What a deadlock looks like in gcs_db

The problem scenario:
User A books an appointment → locks appointments row, then tries to lock counselor_availability
User B updates availability → locks counselor_availability row, then tries to lock appointments
Result: Both wait forever. Neither can proceed.
TimeUser A (booking)User B (updating availability)
T1🔒 Locks appointments row #45
T2🔒 Locks counselor_availability row #12
T3⏳ Waits for counselor_availability #12
T4⏳ Waits for appointments #45
T5💀 DEADLOCK — InnoDB kills one transaction and rolls it back

Strategy 1 — Consistent table access order Primary defense

Every transaction in the application must always lock tables in the same fixed order. This eliminates the circular wait condition entirely.

Our fixed order for gcs_db:

#TableWhy this position
1studentsAll operations start from a student record
2counselorsCounselor is referenced after student is confirmed
3counselor_availabilitySlot is checked before booking is created
4appointmentsBooking row is written after slot is verified
5audit_logAlways written last — never locks anything else

If User A and User B both follow this order, User B will block at step 3 waiting for User A to finish — no circular wait, no deadlock.

Strategy 2 — Row-level locking with SELECT … FOR UPDATE Concurrency control

Instead of locking the whole table, we lock only the specific row we need. This allows multiple users to book appointments with different counselors at the same time.

-- Booking transaction: lock ONLY the specific slot needed
START TRANSACTION;

-- Lock just this one availability row (not the whole table)
SELECT availability_id, is_booked
FROM counselor_availability
WHERE counselor_id = 3
  AND day_of_week = 'Monday'
  AND slot_time = '10:00:00'
FOR UPDATE;

-- If is_booked = 0, proceed
INSERT INTO appointments (student_id, counselor_id, appointment_date, status)
VALUES (250001, 3, '2026-05-19', 'Pending');

UPDATE counselor_availability
SET is_booked = 1
WHERE counselor_id = 3
  AND day_of_week = 'Monday'
  AND slot_time = '10:00:00';

INSERT INTO audit_log (action, performed_by, details)
VALUES ('BOOKING_CREATED', 250001, 'Appointment with counselor 3');

COMMIT;

Two students booking different counselors simultaneously will each lock a different counselor_availability row — they never block each other.

Strategy 3 — Keep transactions short Lock duration

The longer a transaction holds a lock, the higher the chance another user bumps into it. Our rule: no user input happens inside a transaction.

❌ Wrong — lock held while waiting for user:
START TRANSACTION → show confirmation dialog → wait for user to click → COMMIT
The lock is held for seconds or minutes while the user reads the screen.
✅ Correct — all data collected first, then transaction runs:
Gather all input → validate in PHP → START TRANSACTION → INSERT → UPDATE → INSERT → COMMIT
The transaction runs in milliseconds with no waiting.

Strategy 4 — InnoDB automatic deadlock detection Last resort

MariaDB InnoDB (which all your tables use) automatically detects deadlocks and resolves them by rolling back the transaction that has done the least work. Your application must handle this error and retry.

// PHP application code — retry on deadlock
function bookAppointment($pdo, $studentId, $counselorId, $slotId) {
    $maxRetries = 3;
    for ($attempt = 0; $attempt < $maxRetries; $attempt++) {
        try {
            $pdo->beginTransaction();

            // Lock the specific availability slot
            $check = $pdo->prepare(
                "SELECT is_booked FROM counselor_availability
                 WHERE availability_id = ? FOR UPDATE"
            );
            $check->execute([$slotId]);
            $row = $check->fetch();

            if ($row['is_booked']) {
                $pdo->rollBack();
                return ['success' => false, 'reason' => 'Slot already taken'];
            }

            // Insert booking
            $pdo->prepare(
                "INSERT INTO appointments
                 (student_id, counselor_id, status)
                 VALUES (?, ?, 'Pending')"
            )->execute([$studentId, $counselorId]);

            // Mark slot booked
            $pdo->prepare(
                "UPDATE counselor_availability
                 SET is_booked = 1
                 WHERE availability_id = ?"
            )->execute([$slotId]);

            // Audit log
            $pdo->prepare(
                "INSERT INTO audit_log (action, performed_by)
                 VALUES ('BOOKING_CREATED', ?)"
            )->execute([$studentId]);

            $pdo->commit();
            return ['success' => true];

        } catch (PDOException $e) {
            $pdo->rollBack();
            // Error 1213 = deadlock, error 1205 = lock wait timeout
            if (in_array($e->getCode(), ['40001', '1213', '1205'])) {
                usleep(100000 * ($attempt + 1)); // wait 100ms, 200ms, 300ms
                continue; // retry
            }
            throw $e; // other errors: re-throw
        }
    }
    return ['success' => false, 'reason' => 'Could not complete after retries'];
}
